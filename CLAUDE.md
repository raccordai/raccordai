# Raccord — conventions

Electron app (main / preload / renderer). Package manager: pnpm.

## Verification

- `pnpm lint`, `pnpm typecheck`, `pnpm test`, then `pnpm build` before considering a change done (CI also runs `format:check` — run `pnpm format` after edits).
- ESLint (flat config, `eslint.config.mjs`) encodes the no-raw-colors rule; lefthook runs lint+prettier at pre-commit and commitlint (conventional commits, required by release-please) at commit-msg. typescript-eslint runs on its own TS 5.x via `.pnpmfile.cjs` (TS 7's native compiler has no JS API yet) — don't remove that hook.
- Unit tests: Vitest launched through `scripts/run-vitest.mjs` (Electron's embedded Node — never run `vitest` directly, better-sqlite3 is compiled for Electron's ABI). Strategy and coverage rules: `docs/testing.md` — every new logic module ships with its tests and enters `coverage.include` (thresholds are blocking in CI; never lower them or shrink the scope).
- E2E: `pnpm build && pnpm e2e` (versioned suite in `e2e/`, dedicated CI job) — generation + poller, assistant, IPC/MCP, `media://`, MP4 render, all against the local kie mock (no credits, no network). Each spec launches the app with a throwaway `--user-data-dir` + its own local-API port (`RACCORD_LOCAL_API_PORT`), so it never touches the real install. Rules and how to add a spec: `e2e/README.md`. Run it after touching runEngine, chat, the MCP registry or render.
- For a one-off runtime check outside the suite, reuse `e2e/harness/` rather than writing a new driver: `launchApp()` already handles the isolated profile, the mock wiring and the `invoke`/`goto`/`mcp` helpers.

## Rules

- All renderer→main communication goes through a channel declared in `src/shared/ipc/contracts.ts` (zod input/output schemas). Adding a channel = contract + handler in `src/main/ipc/index.ts` + usage through the typed `invoke()`.
- Business logic lives in `src/main/services/`, consumed by IPC **and** by the Hono routes (`src/main/server/`) — never write it in a handler.
- SQLite schema: edit `src/main/db/schema.ts` then `pnpm db:generate`. Migrations are **additive only** (backward compatibility of user databases, hard product requirement).
- No feature-flag system: features ship enabled for everyone (the old `src/shared/flags/` registry was removed at Romain's request; the `flag_overrides` table remains in the schema for migration compatibility but is unused).
- Every user-visible string goes through i18next: add the key to `src/shared/i18n/locales/fr/common.json` **and** `en/common.json` (keys are typed from the fr JSON).
- The router uses a hash history (required under `file://`) — do not remove it.
- **Colors**: pastel palette mandated by Romain (#ff9bc6 / #ffbcd6 / #ffe5f9 / #b7b6ff / #afdeff). Every color goes through the tokens in `src/renderer/src/styles.css` (`accent`=lavender, `highlight`=pink for the main CTA and the logo, `accent-soft`=sky blue, pastel `success`/`danger`/`warning` for states) — never raw color classes. On solid `accent`/`highlight` backgrounds: `text-neutral-900`, never white. `danger` = error states and destructive hover only, never a solid button background.
- **Editor layout**: UI as floating islands (`island` utility in styles.css) above the full-frame React Flow canvas — toolbar on top, timeline at the bottom, panels (params/history/chat) in a right-hand column. Any new panel follows this pattern.
- TypeScript 7: `baseUrl` no longer exists, `paths` must be relative (`./src/...`).
- **Node layout** lives in `src/shared/graphLayout.ts` (dagre grid + overlap resolution), shared by the renderer's "Tidy" button (`autoLayout.ts` is a thin React Flow adapter) and by `importWorkflow`/`createNode` in main — agents omit positions or reuse one coordinate, so main lays the graph out instead of trusting the payload. Never fork this logic.
- **Graph undo/redo**: every graph mutation is journaled by `src/main/services/graphHistory.ts` (per-video before/after snapshots, diff-restore so untouched generations survive an undo; deleted generations are NOT restored). New graph mutations must go through the graph service so they get journaled — and `withGraphHistory` is the single point that broadcasts `event:workflowChanged`. A composite gesture (select + create + connect, checkpoint restore) wraps its calls in `withGraphHistoryGroup` so the whole thing is ONE undo step; nested `withGraphHistory` calls become passthroughs.
- **Checkpoints** (§6.4, `src/main/services/checkpoints.ts`): a named capture stores BOTH the raw rows (`snapshot`, the restore payload — replayed through the same diff-restore as undo, so surviving nodes keep their generations) and the workflow-JSON v1 export (`workflow`, used for the diff and for portability), plus `selections` keyed by node KEY. Never restore through `importWorkflow(replace)` — it deletes every generation of the video. Diff logic is pure in `src/shared/checkpointDiff.ts`; `restore_checkpoint` is `risk: 'destructive'`.
- **Prompt lint** (§6.5, `src/shared/promptLint.ts`, pure + tested): rules derived from the model registry (never hardcoded ids) — empty prompt, missing required input, reference wired but not addressed in the prompt, design sheet on a `frameAnchor` (unless the recipe is `anchorSafe`), recipe node whose required source was never wired (`recipe-source-missing`, read from the `recipeId`/`recipeMode` markers), the §6.9 doctrine rules on the WRAPPED payload (`camera-doctrine-mixed` blocking, `speed-ramps-undeclared`, `caps-transients-overused`, register-aware `anti-ai-lexicon` — pass `styleId` or they degrade to the terms that hurt everywhere), storyboard shot missing `ANTI_GRID_GUARD` (the single source of truth for that sentence lives in `seedance2-prompting.ts`), param outside a field's `options`. Each finding may carry a one-click `fix` (`appendPrompt` / `setParam` / `rewire` — the latter through the journaled `edges:rewire`). Surfaced in the params panel, in the run confirm (`PlannedRow.lint`), as the `lint_node` tool, and folded into the QC verdict by `foldLintIntoVerdict` (a `pass` only degrades on a BLOCKING finding).
- **Regional feedback** (§6.3): notes on a generation (`generation_annotations`, cascade-deleted with it) — a normalized region on an image or a timecode on a clip, plus a comment. Wording is pure in `src/shared/annotations.ts` (regions are described in words, never as coordinates); `createEditNodeFromAnnotations` builds a pre-wired `gpt-image-2-image-to-image` fix node in one undo step and promotes the annotated generation to the source node's selection first. Video outputs have no in-place edit path — their notes feed a regeneration prompt.

## Generation (kie.ai)

- The engine lives in `src/main/services/runEngine.ts` (no webhooks on desktop: the poller IS the completion path; in-flight generations resume on startup via `resumePolling()`, queued-but-unsubmitted ones are re-queued from their input snapshot).
- Submissions go through a **concurrency-limited queue** (`src/main/services/genQueue.ts`, limit = `maxConcurrentGenerations` setting, default 2; a slot is held until the generation settles). `runNode` returns `kieTaskId: ''` while queued. createTask retries transient failures with backoff.
- **Smart retry**: a failed generation (submission error or remote `fail`) is re-submitted from its input snapshot after 5 s, max 3 times, without releasing its queue slot — EXCEPT permanent errors (content-policy violations, 4xx), classified by `isRetryableGenerationError` in genQueue.ts. No retry on poll timeout or user cancellation.
- Each new generation stamps `creditsEstimated` (from the model's `estimateCredits` — **indicative rates declared per model file**, align them with https://kie.ai/pricing); per-project totals via `projects:creditsUsage`.
- **Variants ×N** (`MAX_VARIANTS` in `src/shared/config.ts`, cap 4): one `prepareRun` + N `claimRun`s with `forceNew` (the in-flight dedup is bypassed on purpose), N queue slots, N credit charges. The decision is pure — `planRun` stamps `runs` per entry and multiplies the **explicit targets only** (dependencies stay shared, `runs: 1`), so the cost preview, `run_batch` and the agents share one source of truth; a variants batch must pass `reuseTargets: false` or the satisfied target yields zero candidates. A node is satisfied as soon as ONE candidate succeeds (the first success auto-selects); `cancelGeneration` cancels **every** run in flight on the node. Compare grid + "Use this" in `NodeParamsPanel` (2–4 panes, synced playback/zoom).
- **Style-at-payload**: the style bible is NEVER baked into stored prompts. Visual nodes carry the params marker `applyVideoStyle: true` (default on plainly-created/template/design nodes; stripped by zod at run) and `prepareRun` appends the video's current bible to the prompt BEFORE persisting the input snapshot (deterministic retries). Pre-existing nodes without the marker keep their baked-in prompts byte-identical — never inject the flag into caller-provided params (imports/agents set it themselves). Video-level defaults (`videos.default_aspect_ratio/default_resolution`, Style menu) pre-fill new nodes via the shared `videoDefaultParams` (per-model enum check); existing nodes only change through the explicit journaled `nodes:applyVideoDefaults` sweep (one undo step).
- **New model** = ONE `ModelDefinition` file in `src/shared/models/` + entry in the `MODELS` array (pure data/functions, no Electron imports). Full guide — required fields, UI/engine/docs consumption map, quality checklist: `docs/models.md`. Replacing a model: add the old id to `MODEL_ALIASES`.
- **Image-input semantics — the #1 pitfall**: seedance-1.5 `input_urls`/grok `image_urls`/seedance-2-family `first_frame_url`+`last_frame_url` are FRAME ANCHORS (the image appears on screen); seedance-2-family `reference_*` are REFERENCES (guide only, invisible without a frame role in the prompt). On Seedance 2.x, kie.ai documents THREE mutually exclusive modes per run: first frame only / first+last / @ references. Character sheets/storyboards → references ONLY. Details: `docs/models.md`; templates enforce it by test. Anchor handles declare `frameAnchor: true` on their `InputHandle` (tests + UI guard derive from it — set it on any new anchor input).
- **Last frame is extracted in MAIN** (bundled ffmpeg, `extractLastFrameFromResult` in runEngine.ts, argv in the pure `buildLastFrameArgs` of renderPlan.ts, binaries via `src/main/media/ffbin.ts`): fired right after a video result downloads, so `lastFrame` edges resolve without any window — headless MCP runs included. The renderer's canvas extractor (`generations:setLastFrame`) remains as a BACKFILL for rows that predate this; the `lastFramePath` first-writer-wins guard keeps the two race-safe.
- **Scenario** (§6.7, `src/shared/scenario.ts` pure + tested; docs topic `scenario`): the step between a brief and the graph. The assistant writes BEATS (`write_scenario`), `planScenario` returns SHOTS that are legal by construction — sub-floor beats run AT the model's floor (`shortBeatPolicy: 'stretch'`, the default, keeps the cut list) or fold into a neighbour (`'merge'`, keeps the film's length), over-ceiling beats split, everything snapped through `clampParamToField` — chained (each shot's `opensOn` is the previous `closesOn`), reconciled with `targetSeconds`, with a `promptScaffold` per shot the prompts are written on top of. Everything it changed comes back in `warnings` (including a screen-direction reversal across a cut); the assistant must report them. Stored on `videos.scenario` (additive JSON column, zod mirror in `contracts.ts` guarded by a compile-time `Exactly<>` check), read back with `get_scenario`, summarized in `get_workflow`, shown in the editor's Scenario island (`ScenarioPanel.tsx`) — edits go through the assistant so one author keeps shot list, durations and graph consistent. Each shot also carries `roles` (cast role NAMES, §6.10): who is in a shot is the one thing §6.11 cannot derive.
- **Scenario → graph** (§6.11, `src/shared/scenarioGraph.ts` pure + tested, `src/main/services/scenarioGraph.ts`): the deterministic last mile. `matchShotRecipe` picks a SHOT preset from the shot's free-text `camera` line (keyword rules over an accent-folded haystack, fr+en; motion beats framing, `matchShotSize`/`matchPace` read the rest independently), falls back on the shot's place/length/screen direction, and substitutes down a declared chain (ending on `shot-locked-off`) when the scenario's model cannot run the matched preset — every degradation comes back as a `note`, never silent. `buildGraphFromScenario` then creates one node per shot through `createRecipeNode` (the single creation path, so markers and per-model params travel with it), keyed by the shot's own `key`, then calls `castRole` for the roles each shot names — all inside ONE `withGraphHistoryGroup`. Idempotent by node key: re-running after extending the scenario adds only the new shots (`alreadyBuilt`), and a no-op build costs no undo step. It NEVER wires shot to shot (between shots you cut). `planScenarioGraph` is the free dry run the Scenario panel shows before building. Duration is the subtle part: `recipeNodeParams({durationSeconds})` snaps it through `clampParamToField` and feeds BOTH `params.duration` and the prompt's beat timeline (`RecipePromptArgs.durationSeconds`) — a shot preset's prompt IS a timeline, so the two can never disagree. Surfaces: IPC `scenario:planGraph`/`scenario:buildGraph`, MCP/chat `build_graph_from_scenario` (`plan_only`), the Scenario panel's build button.
- **Param bounds are an API contract**: every `number` paramField declares `min`/`max` (+ `step` for discrete sets) — registry-test enforced. `clampParamToField` (shared) is the single clamp used by the params panel and by the lint's `param-out-of-range` fix; `list_models`/`docs "model:<id>"` publish the range to agents (an agent that cannot see the 4 s Seedance floor plans 2 s beats); `describeParamsError` renders a run-time zod failure in the model's own vocabulary. Handles declare `maxCount` and `maxTotalSeconds` (Seedance 2: 15 s of reference video), the latter checked by the `reference-budget-exceeded` lint rule against the sources' declared durations.
- **Transitions** (`src/shared/shotContinuity.ts`, pure + tested; docs topic `continuity`): shared references keep identity stable but do NOT make two clips one sequence. Four layers, cheapest first — shared refs → the written contract (`TRANSITION_CONTRACT`: each prompt states the frame it OPENS ON and the one it CLOSES ON, continuous screen direction, no crossing the 180° line) → a 4-panel **shot board** per shot (design recipe `shotboard`, panel 1 = opening frame, panel 4 = closing frame) → the previous CLIP as an `@Video` reference via `link_shots` (`services/continuity.ts`, one undo group, budget-aware `skipped` list). The last layer serializes the batch and invalidates downstream shots on a re-roll: the assistant proposes it with its cost, never applies it by default. Design recipes that produce a panel grid carry `board: true` — the lint derives the anti-grid requirement from it, never from an id.
- **Prompting doctrine** (§6.9, `src/shared/prompting/seedance.ts`, pure + tested; docs topic `doctrine`): the prompting knowledge used to be prose only an LLM could apply — it is now DATA plus an assembler, enforced on three surfaces. (1) **Capture declarations** (`CAPTURE_DECLARATIONS`): the 15-40 word opening that selects the generative domain — medium, era, rig/operator, light, imperfection, verdict. It is PROVENANCE, so it belongs to the art direction: each `StyleTemplate` declares a `captureId` and a `styleBibleCompact`, and the declaration's `mode`/`doctrine`/`boosterId` are read from it (nothing to keep in sync). (2) **The sandwich**: `wrapPromptWithStyle` composes declaration + compact bible ON TOP, the stored prompt in the middle, the booster stack at the BOTTOM — applied by the run engine to video nodes carrying `applyVideoStyle` (stills keep the historical bible append). It is idempotent: a body already opening on a declaration is returned untouched, so a retry replaying a snapshot can never stack two universes. (3) **The camera is a body or a ghost** (`CameraDoctrine`), never both — `camera-doctrine-mixed` is a BLOCKING lint finding. Shot presets therefore ship three phrasings (`motion` instrument / `operator` body / `ghost`) and pick by the video's register; a film has ONE register, which is why it lives on the style (`kinetic-action` is the stylized one) and not on the node. Also encoded: the bracket vocabulary (`CAMERA_MODES`, kinetic brackets require the ghost), the FOV anchor table (`snapFov` — degrees only, never mm), shot sizes, Kelvin white balance, per-medium imperfections, and the register-aware anti-AI lexicon. New declaration/booster/bracket = one entry + the registry test (word window, own medium detectable, one doctrine, booster register match).
- **Between shots you CUT, never chain**: wiring a clip's `lastFrame` into the next clip's image input glitches the seam (a generated closing frame is motion-blurred and compressed, so the next clip re-interprets a degraded still). Every shot is a new camera setup; consistency comes from the SAME references wired on all of them. Genuine continuity uses video extend (previous clip → `reference_video_urls`); on models without references (1.5, Grok), several shots may re-anchor on the same clean source still. No template ships a `lastFrame` chain — the handle stays available for manual use. This doctrine is stated in both chat SYSTEM prompts, `seedance2-prompting.ts`, every video model's `promptingNotes` and `docs.ts`; keep them in sync.
- **Recipes** (§6.8, `src/shared/designs/registry.ts`, pure + tested): ONE registry for every pre-configured node, in two `kind`s. `reference` recipes (character/decor/prop/styleframe/expressions/wardrobe/packshot/shotboard/storyboard) produce a design SHEET and carry `params.designId` — the marker the frame-anchor guard, the anti-grid lint and the design library key off. `shot` recipes (`shot-establishing`, `-tracking`, `-push-in`, `-pull-back`, `-orbit`, `-insert`, `-reaction`, `-pov-handheld`, `-whip-pan`, `-locked-off`, `-extend`) produce a VIDEO node with the camera move already written, and deliberately carry NO `designId` (it would fire the sheet rules on a clip). `RECIPES` is the whole list; `DESIGN_RECIPES`/`SHOT_RECIPES` are the two views; `getDesignRecipe` never resolves a shot.
  - **Fields, not a textarea**: each recipe declares `fields: RecipeField[]` from the shared `RECIPE_FIELDS` vocabulary (field 0 is always `description`). A `select` option carries the prompt `fragment` it injects — that is what makes the form testable, and the registry test enforces i18n parity in BOTH directions under `recipeFields.<key>.{label,placeholder,options.<value>}` (fr+en). `screenDirection` mirrors `SCREEN_DIRECTIONS` from `scenario.ts` (test-enforced), so a scenario's shots feed a shot preset verbatim.
  - **Modes**: `text` / `from-image` / `from-video`. A mode declares its `modelId` and, when it needs media, a `source` by ROLE (`anchor` | `reference`) — never a handle key: `resolveRecipeHandle` derives the key from the model registry, so the same recipe runs on models that name their inputs differently. `recipeModelChoices` is the single rule for which models a mode offers (the form, the creation service and the test all read it). A `from-image` reference recipe MUST declare the `preserve` field (registry-tested) — without a preservation clause an image-to-image sheet drifts every iteration.
  - **`anchorSafe`**: `styleframe` and `packshot` may legitimately BE a frame. Without that flag "came from a recipe" and "must never appear on screen" are the same bit, and the frame-anchor guard errors on a correct wiring. Boards are never anchor-safe.
  - **Creation goes through main**: `src/main/services/recipes.ts` (`createRecipeNode`) — IPC `recipes:createNode` **and** the MCP/chat tool `add_recipe_node`, so the prompt-building knowledge reaches agents without a copy. It creates the asset node + the recipe node + the edge inside ONE `withGraphHistoryGroup`. The renderer only PREVIEWS the prompt, with the same pure `buildRecipePrompt` — the preview cannot drift from the result.
  - **Templates never re-copy a recipe prompt**: `recipeNode()` in `src/shared/templates/registry.ts` builds those blueprint nodes from the registry, so the markers travel with them and the lint protects a template-born graph too.
  - New recipe = one entry in `RECIPES` + i18n `designs.<id>.{name,desc,placeholder}` (fr+en); new field = one entry in `RECIPE_FIELDS` + `recipeFields.<key>.*`. The MCP `docs "designs"` and `docs "shots"` topics are generated from the registry. A shot preset earns its place by satisfying `mentionsMotion` BY CONSTRUCTION (registry test) — a preset that does not turn a lint warning green is decoration.
- **Casting** (§6.10, `src/shared/casting.ts` pure + tested, `src/main/services/casting.ts`; docs topic `casting`): the film's NAMED identities, project-scoped (`castings` table — name unique per project, `asset_id` cascades). The library records what a sheet IS (`design_id`) and what it depicts (`design_subject`); the casting records who that is for the film — "Léa IS that sheet". `castRole` wires the role's sheet as a reference on every video shot AND appends its identity sentence to each prompt inside ONE `withGraphHistoryGroup`; the sheet fans out from a SINGLE `studio/asset` node, reused when one already points at that asset (which is also what makes "already cast" detectable). Idempotent — a second pass reports `alreadyCast` with the alias the shot already answers to, never a duplicate edge nor a second sentence — and budget-aware: a shot whose reference handle is full, or whose model has no reference-image input (Seedance 1.5, Grok), lands in `skipped` with a reason. `planCastRole` is the free dry run the editor shows before spending an undo step. This is `continuity.ts` for IDENTITY instead of continuity and must stay shaped like it (handle derived from the model registry, plan before mutating, skip instead of overrun); what differs is the sentence — continuity points BACKWARD at one shot, casting names the identity and asks for it across shots. Deleting a role touches no graph. Surfaces: IPC `casting:*`, MCP/chat `list_castings`/`create_casting`/`update_casting`/`cast_role`/`remove_casting`, the project page's Casting tab and the editor toolbar's cast menu.
- **Design library**: promoting a design node's generation (`assets:promoteGeneration`) copies its `params.designId`/`designSubject` markers onto the asset (`assets.design_id/design_subject`) → the sheet becomes reusable project-wide (filter chips in the Assets tab and the node picker, "From the library" entry in the add-node Designs group creating a pre-wired `studio/asset` node). The frame-anchor confirm also fires for asset nodes whose asset carries a `designId`; `assets:references` lists the videos using an asset before deletion. Agent side: `publish_design` + `search_assets` (chat **and** MCP — keep both toolsets in sync) and design fields in `get_workflow`/`list_assets`.
- **Storyboard** = the pre-visualization step between design sheets and video (Seedance 2.x): one 3x3 grid of 9 numbered panels showing the scene beat by beat, built FROM the sheets (`gpt-image-2-image-to-image` via the recipe's `byModel` override) at the video's aspect ratio, reviewed by the user BEFORE spending video credits, then wired as a reference with the role "@ImageN is the 9-panel storyboard — follow its panels in order, left to right, top to bottom" (each shot says which panels it covers; the video prompt describes motion, not visuals). Blueprint: template `storyboard-sequence`; guidance lives in `seedance2-prompting.ts`, `docs.ts` (designs/models/continuity topics) and both chat SYSTEM prompts. On short clips (4-6 s) the per-shot `shotboard` recipe replaces that single panel with its own 2x2 board — the two coexist (the storyboard covers the sequence, the board covers the cut).
- **Template slots** (`src/shared/templates/registry.ts`): every `[TOKEN]` in a blueprint is declared metadata (`slots: {token, i18nKey, example}[]`, shared `SLOTS` vocabulary) — the registry test enforces token↔blueprint parity in BOTH directions and fr/en label resolution, so adding/removing a token in a prompt requires updating `slots` (and vice versa). `fillTemplateSlots` is the single fill path (new-video slot form + onboarding starter project); blank values keep their token (assistant-fillable later).
- **First-run onboarding**: `onboardingCompleted` setting; overlay in `src/renderer/src/features/onboarding/FirstRunOverlay.tsx` (language → kie key with live validation via `settings:testKieApiKey` (never throws, classifies ok/unauthorized/network/missing) → starter project); back-filled as completed at startup when a kie key already exists (`backfillOnboardingCompleted`, main/index.ts). `__root.tsx` shows a missing-key banner once onboarding is done (hidden on /settings).
- The API key is encrypted with `safeStorage` (never in the clear outside the main process). One exception, unreachable in a real install: on Linux with no OS keyring safeStorage refuses to encrypt at all, so `main/index.ts` calls `setUsePlainTextEncryption(true)` when `!app.isPackaged && RACCORD_E2E === '1'` — that is the only way the E2E CI job can store a key. Local input media are uploaded on demand to kie.ai's File Upload API (48h TTL cache in the database; files expire on kie's side after ~3 days).
- **Credit-free E2E**: `RACCORD_KIE_BASE=http://127.0.0.1:<port>` points the whole client (`src/main/services/kie.ts`) at `e2e/harness/kie-mock.mjs`, which serves every kie surface — jobs createTask/recordInfo, Suno generate/record-info, file-stream-upload, chat/credit, the Claude proxy — plus the result media itself, and records what the app submitted (`mock.recorded`) so specs can assert the payload, not just the outcome.

## Rendered MP4 export

- Entry points: `render:export` IPC (native save dialog in the handler, progress via `event:renderProgress`, cancel via `render:cancel`) and the MCP `render_video` tool (headless, explicit/default output path). Both call `src/main/services/render.ts`. **Export options**: `quality` (draft/standard/high) + `codec` (h264/hevc) via `encodeArgsFor` (renderPlan) — 'standard' h264 IS the historical encoder args byte for byte, threaded through every encoding builder; an explicit hevc request forces the normalize path (stream copy can't transcode) while a quality choice alone keeps lossless.
- **Split**: `renderPlan.ts` holds ALL decisions (ffprobe parsing, lossless-concat-vs-normalize, ffmpeg argv builders, progress mapping) — pure, unit-tested, in `coverage.include`; `render.ts` only spawns/files (E2E scope, like runEngine). New render behavior goes in renderPlan + tests, not inline in render.ts.
- **Timeline resolution is `src/shared/timeline.ts`** (`collectTimelineClips`/`bestGeneration`/`clipDuration`/`collectAudioNodes`): the single source of truth shared by TimelineV2, the FCPXML export and the MP4 render — never fork this logic.
- **Timeline editing** lives on the NODE rows (additive columns `timeline_order`, `trim_start_sec`, `trim_end_sec`, `transition_after`), mutated ONLY through the journaled graph service (`setTimelineOrder` — one undo step for the whole sequence, `setClipTrim` — validated once for every surface, `setClipTransition`) via IPC `nodes:setTimelineOrder/setTrim/setTransition` and the MCP tools `set_timeline_order`/`set_clip_trim`/`set_clip_transition`. The shared readers are `clipTrim` (clamped — never read the raw columns), `trimmedClipDuration`, `clipTransitionAfter` and `CROSSFADE_SECONDS`; an explicit `timelineOrder` beats the label-number ordering and disables the same-number replacement dedupe. All three consumers honour them: TimelineV2 (drag-reorder, scissors popover, playback bounded to the trim window — a trimmed clip advances from the clock tick, and `advance` pauses the outgoing video or its late `ended` double-advances), the FCPXML export (spine `start` = in-point) and the MP4 render. **Split/razor (§6.12e)**: additive `nodes.segments` JSON — null = ONE implicit segment read from the historical trim/transition columns (byte-compat), else each segment carries its own trim window + transition. `clipSegments` normalizes, `collectTimelineEntries` expands the timeline into (node, segment) ENTRIES — the resolution the player and the MP4 render now consume (`segmentTrim`/`segmentTransitionAfter`/`segmentTransitionSeconds`, never the raw columns on a split clip). Mutations (all journaled): `splitClip(nodeId, atMediaSec)` (media time, ≥0.2 s from each edge; the original transition stays on the SECOND half), `removeClipSegment` (the last two collapse back to columns), `setClipTrim`/`setClipTransition` with `segmentIndex`. The legacy columns stay synced to the segments' ENVELOPE (first in-point, last out-point, last transition) so column-only readers (FCPXML) degrade to the overall window instead of a stale state. Reordering stays NODE-grained (segments are always adjacent — the deliberate trade of segments-on-the-node vs a timeline_clips table). ## Niche research YouTube (§7)

- **The object**: a niche is an APP-LEVEL watchlist (not project-scoped) — tables `niches`/`niche_channels`/`niche_videos` (cascade on the niche; `is_mine` flags the user's own channels; `niches.description` is the positioning brief the assistant reads AND writes). ## Assistant (Anthropic chat)

- Service in `src/main/services/chat.ts`: agentic Messages API loop with tools wired to the SAME services as IPC. Conversations are **threads** keyed by an opaque `threadId`, persisted in SQLite (`chat_threads` via `chatStore.ts` — transcript, Anthropic history and watched generation ids survive restarts; `busy` never persists); the renderer syncs via `chat:get` + `event:chatUpdate` (payload `{threadId}`) and graph mutations push `event:workflowChanged`.
- **Threads**: `chat_threads.video_id` is nullable and has NO foreign key — a conversation outlives its video (`deleteVideo` calls `unbindThreadsOfVideo`). `videoId === null` ⇒ home prompt + explicit-id toolset; that is the ONLY source of `isHome` (never the session key, which would be injected as a videoId). New threads keep `projectId: ''` — inheriting the viewed project would pin them to it forever. The old `chat_sessions`/`chat_home_session` tables remain, read once by `backfillChatThreads` (idempotent through the `chatThreadsBackfilled` setting, not an emptiness check); `ensureDefaultThread()` then guarantees one selectable row.
- **Settle wake-up lookup**: `findThreadIdsWatching(generationId)` queries the store — thread ids are opaque, so nothing can be derived from the event, and the query also reaches threads that are not in memory (a generation still polling across a restart).
- **Home assistant** (Assistant button on the home page): session key `HOME_CHAT_ID` ('home', own table `chat_home_session` — chat_sessions has a videos FK), prompt SYSTEM_HOME + toolset TOOLS_HOME = project tools (create_project/create_video/list_*) + the graph tools with an explicit required `videoId`. - **Credit-free assistant E2E**: `pnpm test:assistant` (= `pnpm e2e assistant`, `e2e/specs/assistant.e2e.mjs`) scripts the Claude proxy with an agent that runs create_project → create_video → set_video_style → import_workflow, and asserts the project/video/graph really exist. Run it after touching chat.ts, the MCP registry or the docs topics.
- **Run approval** (`assistantRunApproval` setting, Settings → General, default `ask`): the `risk: 'spending'` tools (`run_node`, `run_batch`, `finalize_video`, `review_generation`) go through the SAME approval card as the destructive ones, with the estimated credit cost on the label. The gate is hoisted ABOVE the `executeTool` switch in chat.ts — `run_batch`/`finalize_video` have their own `case` and would otherwise bypass it. `finalize_video` with `plan_only: true` is a free preview and is exempt. `approvalGate` stays pure (policy passed in); the mode is also appended to the system prompt per turn, since the prompt is static and the setting is not.
- **Automatic wake-up**: generations launched through the `run_node` tool are watched (`session.watched`); on completion the run engine emits `generationSettled` on the in-main bus (`src/main/bus.ts`) and the chat **resumes the conversation on its own** (injected `<system-reminder>` note + new turn). - **Prompt caching** (`chatCache.ts`, pure + tested, in coverage): the Claude-proxy path stamps three `cache_control` breakpoints per call — last tool, system, last block of the last message — so each loop iteration only pays the delta instead of re-reading ~60 schemas + SYSTEM + history. ## Known pitfalls (media & islands)

- The `media://` scheme must stay registered with `standard: true, stream: true, supportFetchAPI: true, corsEnabled: true` (privileges in `src/main/media/protocol.ts`) — without `standard`, Chromium rejects every media/fetch request from `file://`. The handler must serve **Range requests** (206 + Content-Range) or `<video>` elements won't play, and must answer OPTIONS preflights (fetch with a Range header).
- The CSP (`src/renderer/index.html`) must keep `media:` in `img-src`, `media-src` **and** `connect-src` (the FCPXML export fetches local media).
- The `island` utility deliberately has NO `overflow: hidden` (toolbar dropdowns must be able to overflow) — scrollable panels add it themselves.
- **Chromium `backdrop-filter` + `<video>` bug**: an ancestor with backdrop-filter makes videos invisible to hit-testing (controls render but receive no clicks). Mandatory workaround in styles.css: `.island video { position: relative; z-index: 1 }`. Any new blurred container hosting a video must keep this rule (diagnosed by bisection: removing the blur restores clicks). CAUTION: that rule is unlayered so it beats Tailwind's `absolute` utility — videos that must be absolutely-positioned overlays (TimelineV2's A/B player) need the `.video-stack` container class, whose rule restores `position: absolute` (otherwise the standby video is pushed out of frame → black player from clip 2 on).
- React Flow v12 selectors: panels carry separate classes (`.bottom.left`), and the minimap IS its own panel (`.react-flow__minimap.bottom.left`).
- **Draggable title bar**: the header has `-webkit-app-region: drag` — any interactive element placed in it MUST be covered by the no-drag rule in styles.css (`a, button, input, select`), otherwise its clicks are swallowed by window dragging. The same swallowing kills _document-level_ listeners: a `document` pointerdown never fires for clicks on the drag region, so an outside-click dismissal appears broken over the title bar. `MenuBar` handles it with a `no-drag fixed inset-0` overlay while a menu is open — and the menu wrappers carry `relative z-50` so that overlay (z-40, a sibling) doesn't cover the triggers themselves.
- **Dismissing menus/popovers**: always `useDismissable(open, close, ref)` (`components/ui/useDismissable.ts`) — outside pointerdown + Escape, capture-phase so a search input inside can't eat Escape first. Never `onBlur` + `setTimeout` (only fires when the click lands on something focusable) and never a `fixed inset-0` catcher (it eats the click it was aimed at). The trigger's own `setOpen((v) => !v)` provides re-click-to-close; the hook ignores clicks inside `ref` so the two don't fight.
- **Keyboard shortcuts**: one registry, `src/renderer/src/lib/shortcuts.ts` (`SHORTCUTS` + pure `matchesShortcut`/`formatShortcut`/`isTypingTarget`, unit-tested and in `coverage.include`); bind with `useShortcut(id, handler)` (`components/ui/useShortcut.ts`), which applies the typing guard. A menu entry declares `shortcut: <id>` to render the combo — the binding itself still has to be registered by the owning component. `mod` = ⌘ on macOS, Ctrl elsewhere; a registry test enforces no two actions share a keystroke.

## Errors & logging

The packaged channel (`updateChannel` setting, stable|beta, Settings → Updates) drives BOTH the update feed (beta = `allowPrerelease`, i.e. GitHub prereleases `vX.Y.Z-beta.N` — never set `autoUpdater.channel` with this provider) and `getReleaseChannel()`. Dev builds: updater is a no-op ('unsupported'). macOS installs updates only on a signed app — until notarization ships, mac update attempts end in 'error'.
- **Release pipeline**: release-please tags/creates the GitHub release, then `publish-release.yml` (chained job — `release:` events never fire from GITHUB_TOKEN-created releases) builds the 3 OS and uploads installers + `latest*.yml`/blockmaps + stable-named aliases (`Raccord-mac.dmg`, `Raccord-windows.exe`, `Raccord-linux.{AppImage,deb}`) for permanent `releases/latest/download/...` links; it also has a manual `workflow_dispatch` on a tag for backfills. macOS is signed + notarized there via repo secrets (`MAC_CSC_LINK` base64 .p12, `MAC_CSC_KEY_PASSWORD`, `APPLE_ID`, `APPLE_APP_SPECIFIC_PASSWORD`, `APPLE_TEAM_ID`); electron-builder skips notarization with a warning when they are absent, so PR/fork builds stay unsigned but green.
